# Site Planning Skill

## Purpose

Turn a structured site brief into a clear information architecture and page plan before any visual layout or component work begins.

The plan should reflect the organisation's goals, the visitor's needs, and the most important actions the site must support.

Do not begin page composition until the site plan is coherent.

## Inputs

Use the available structured requirements, such as:

- organisation or business description
- target audience
- primary user goals
- primary business goals
- products or services
- important content
- required functionality
- available brand assets
- existing site structure, if provided
- constraints and compliance requirements

If the brief is incomplete, make only the smallest reasonable assumptions and record them explicitly.

## Planning Sequence

### 1. Identify the site's primary purpose

State in one sentence what the website must accomplish.

Examples include:

- generate enquiries
- drive bookings
- explain a service
- sell products
- present a portfolio
- provide information
- support existing customers

Avoid vague goals such as "look professional" unless they are tied to a user or business outcome.

### 2. Identify priority audiences

For each significant audience, determine:

- who they are
- what they are trying to achieve
- what information they need
- what may prevent them from acting
- what action the site should make easy for them

Do not create personas unless they materially improve the planning decision.

### 3. Define primary user journeys

Map the smallest number of important paths through the site.

Typical journeys may include:

- discover business → understand offer → establish trust → contact
- choose service → compare options → view proof → enquire
- find product → inspect details → purchase
- discover venue → inspect menu or offering → check location → book

Prioritise journeys by importance. Do not treat every possible visitor path as equally important.

### 4. Determine page inventory

Create only pages that have a distinct purpose.

For each page, define:

- page name
- audience
- primary purpose
- primary user action
- supporting actions
- required content
- evidence or trust content
- relevant relationships to other pages

Avoid creating separate pages merely because a common website template usually contains them.

### 5. Define navigation

Navigation should reflect user intent, not internal organisational structure.

Rules:

- keep top-level navigation concise
- place the most important destinations first
- use labels users immediately understand
- do not hide primary conversion paths
- avoid unnecessary dropdown depth
- do not place low-priority legal or utility links in primary navigation

Define desktop and mobile navigation expectations at planning time.

### 6. Establish content hierarchy

For every important page, rank content by importance.

Use three levels:

1. **Primary** — content required to understand the page and take the intended action
2. **Supporting** — content that answers likely questions, builds confidence or explains details
3. **Optional** — content that may enrich the page but is not necessary for its core purpose

Do not allow optional content to dominate primary content visually or structurally.

### 7. Define calls to action

Each page should have a clear intended next step.

Classify calls to action as:

- primary
- secondary
- contextual

Avoid filling a page with several equally prominent competing CTAs.

CTA wording should describe the actual action where possible.

Prefer specific actions such as:

- Book a table
- Request a quote
- View services
- See the menu
- Start an enquiry

over vague labels such as "Learn more" when a clearer action is available.

### 8. Identify proof and trust requirements

Determine where visitors need reassurance before acting.

Possible trust content includes:

- testimonials
- reviews
- case studies
- qualifications
- awards
- client logos
- guarantees
- process explanations
- pricing clarity
- location or contact details
- real project or product imagery

Use proof where it resolves uncertainty. Do not add decorative social proof simply because it is a common website pattern.

### 9. Plan cross-linking

Define logical relationships between pages and content.

Important content should not become isolated.

Useful links should follow user intent, for example:

- service → relevant case study
- menu → booking
- product category → product detail
- article → relevant service
- about → team or contact

### 10. Check scope discipline

Before completing the plan, remove:

- redundant pages
- weak duplicate sections
- content added only to make the site feel larger
- generic template pages without a clear purpose
- unnecessary CTAs
- navigation items that belong in the footer

## Required Output

Produce a structured site plan containing:

### Site objective

One concise statement of the site's main purpose.

### Priority audiences

List audiences with their main needs and intended actions.

### Primary user journeys

List the most important paths through the website.

### Sitemap

For each page include:

- page name
- purpose
- primary CTA
- major content blocks

### Navigation model

Define primary navigation, utility navigation if needed, and footer destinations.

### Page priorities

Identify which pages are:

- essential for initial release
- useful but secondary
- candidates for later expansion

### Assumptions

Record any material assumptions made because requirements were incomplete.

## Quality Checks

Before passing the plan to page composition, confirm:

- every page has a distinct purpose
- navigation labels are understandable without explanation
- primary business goals map to actual user journeys
- every major page has a clear intended next action
- the sitemap is no larger than necessary
- content hierarchy is explicit
- trust content is placed where visitors actually need reassurance
- the plan does not simply reproduce a standard template structure

## Completion Standard

The site-planning stage is complete when another agent can read the plan and understand what pages to build, why each page exists, what each page must contain, and what users should do next without inventing the site's structure during implementation.
